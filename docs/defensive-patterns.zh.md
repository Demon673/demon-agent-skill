# 防御模式

[English](defensive-patterns.md) | 中文

踩坑总结出的缺陷分类规则：下文每种模式都是本文档所源自的 harness 中真实上线过、或险些流入线上的缺陷类别，表述为防复发规则。编写生命周期、并发、子进程或销毁相关代码前请先阅读本文档。

## 独立上报正交结果

一个结果可能同时是多种事实——进程可能既超时又以 0 退出，因为它捕获了信号。每个独立事实（`timedOut`、`signal`、`exitCode`）单独呈现；绝不在一个标志的分支里嵌套上报另一个标志，否则调用方会把被截断的运行读成干净的成功。

## 在两侧都遵守公共契约

当一个实现接收到同一结果的多种表示时，在通过公共 API 返回前先做归一化。一个流可能抛出异常，也可能发出终止的 `finish` 事件；以单一文档化形式暴露失败，并通过真实消费方演练每一种来源形式，这样调用方就无需猜测捕获到的异常究竟来自提供方、包装层、日志还是自身组装。

## 异步状态不是同步状态

未完成的请求就是未完成：后台任务的完成与轮次边界存在竞态；关闭回调既会在输入结束时触发，也会在销毁时触发。绝不要用刚刚发起的状态去门控控制流——以实际触发的事件或 promise 驱动生命周期，观察状态变化（先 `running` 再 `idle`），并显式处理「无可等待」分支，因为一个永远不可能发生的待等待转换会导致挂起。

## 销毁必须达到静默，而非仅仅请求它

只发出 kill 或 abort 却不等任务停止就返回的销毁，会留下孤儿。让清理异步化并等待子任务退出（kill → await `done`），在 kill 之前先关闭监听器或通知注册表，让迟到的完成保持静默。测试要证明销毁确实等待了，而不是进程最终才消亡。

## 在分发器中包容回调异常

用户提供的监听器抛出异常，绝不能拒绝它所在的 promise，也不能饿死其后的监听器。用 try/catch 包裹分发循环并记录日志；一个坏订阅者绝不破坏核心生命周期。

## 绝不让不受信任的输出接触环境或可预测路径

被启动的命令获得被清洗过的环境（去掉 `*KEY*` / `*SECRET*` / `*TOKEN*` / `*PASSWORD*`），使凭据不会泄漏到输出、`env` 或溢出文件中。临时与溢出文件使用私有（0700）目录、随机文件名和独占的仅属主打开方式——可预测且全局可读的路径会招致符号链接竞争和泄露。

## 解链链接形路径

可能是符号链接或 junction 的路径，先检查 `lstat` 再解链：unlink 只删除链接本身并拒绝真实目录，因此它绝不会顺着链接进入其目标。递归删除仅用于已知的真实目录。
