# 双语文档

[English](README.md) | 中文

本仓库的文档同时面向两种语言的使用者，因此每个纳入范围的文档都同时维护英文和简体中文两个版本。本页定义配对契约、门禁、范围和排除项；[terminology.md](terminology.md) 是术语的权威来源。常规的对应版本更新直接进行；扩展的 [`translate-docs`](../../skills/agent/translate-docs/SKILL.md) 工作流仅在用户显式调用时运行。

## 配对契约

- **两种语言具有同等效力。** 文档可以先以任一语言撰写；对应版本由它翻译而来。两者之间的约束是必须表达相同的内容。
- **一对是三个同级文件。** 英文 `foo.md`、中文 `foo.zh.md`，以及一致性记录 `foo.i18n.yaml`，位于同一目录。不使用语言子目录，也不使用交织的双语文件。一对文件整体落地：PR 不能只合并一种语言而不合并另外两个文件。
- **语言切换链接。** 紧接 H1 标题之后，每一侧都链接到对应版本：英文侧为 `English | [中文](foo.zh.md)`，中文侧为 `[English](foo.md) | 中文`。
- **结构与对应版本保持一致。** 标题层级与顺序、列表类型与起始值、列表条目数量、表格行列数量、链接目标以及逐字代码块在两侧保持一致。代码块逐字节相同，包括其中的注释。

一致性记录保存两侧在上一次确认表达相同内容时的完整 git blob 哈希：

```yaml
foo.md: 3f786850e387550fdab836ed7e6dc881de23001b
foo.zh.md: 89e6c98d92887913cadf06b2adb97f26cde4849b
```

用的是 blob 哈希而非提交哈希，因此记录可以在同一变更中编辑的文件上计算，一致性是纯粹的内容比较。编辑任一侧而不重新记录配对，就会变红。

## 门禁：verify-translation-pairing

`node scripts/verify-translation-pairing.mjs` 以机械方式执行该契约：

1. 每个纳入范围的文档都有一个完整的三件套：三个文件都在。
2. 每一侧当前的 blob 哈希等于记录值；中文侧和每个英文撰写源都携带切换链接。
3. 结构签名按顺序匹配：标题层级、逐字代码块、表格行列数量、列表类型与起始值、条目数量，以及除切换链接外的每一个链接目标。

三种模式：`--list` 打印每个纳入范围文档的状态（missing / out-of-sync / ok）且永不失败；`--write <pair>`（或 `--write --all`）在你确认配对后重新记录两个哈希；`--check` 校验整个语料，且是无参数时的默认模式。

门禁的局限要说明白：绿灯意味着配对在这些确切内容上被确认一致，而不是确认本身可靠。它检查哈希和 Markdown 结构；它无法判断两侧是否真的表达了相同内容——那是评审者的一半契约。对应版本粗糙的重新记录可以通过门禁；但它绝不能通过评审。

## 范围与排除项

**纳入范围**：`docs/` 下的所有内容文档，以及 `.agents/notes/` 中活跃的 Agent Note 生命周期目录（`proposed/`、`implemented/`、`rejected/`）。

**排除项**（永不配对，门禁会拒绝它们的 `.zh.md` 或 `.i18n.yaml`）：

- 名为 `AGENTS.md` 的指令文件（根目录、`docs/`、`.agents/notes/**/`）——与根目录 `AGENTS.md` 一样仅维护英文。
- `SKILL.md` 文件——仅英文，因为 frontmatter 中的 `name` 和 `description` 必须使用英文以便被发现。
- `docs/i18n/terminology.md`——本身就是双语结构；它是一张表，不是翻译配对。
- `.agents/notes/archived/`——封存的历史三件套；封存门禁校验它们的完整性和内容封印。

## 分工

常规的对应版本由工作 agent 在加载 [terminology.md](terminology.md) 后单次直接更新；普通的更新不调用翻译 skill，也不委派给子 agent。扩展的 [`translate-docs`](../../skills/agent/translate-docs/SKILL.md) 工作流——整篇翻译、简报、委派翻译——仅用于用户显式调用。翻译质量和术语仍由评审负责。
